# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

pnpm workspace monorepo. Node `^24.4.0`, pnpm `>=10.22.0`.

- `apps/dokploy` — Next.js app (Pages Router) plus a custom Node HTTP server. The main UI + tRPC + WebSockets + BullMQ deployment worker. This is what users interact with.
- `apps/api` — Hono service (port 4000) wrapping Inngest for deployment orchestration.
- `apps/schedules` — Hono service (port 4001) running BullMQ workers for scheduled jobs.
- `apps/monitoring` — Go service (separate toolchain, see `apps/monitoring/main.go`).
- `packages/server` — `@dokploy/server` workspace package. **All shared business logic lives here** (services, DB schema, Drizzle setup, builders, Traefik config, auth, access control, queue-adjacent utils). The other apps consume it via `workspace:*`.

The `canary` branch is the source of truth — PRs target it, not `main`.

## Common commands

Run from the repo root unless noted:

```bash
pnpm install
pnpm run dokploy:setup          # spin up postgres/redis containers + run migrations (one-time)
pnpm run server:script          # toggle @dokploy/server to src mode for dev (see "Server package dev/prod modes" below)
pnpm run dokploy:dev            # dev server on http://localhost:3000

pnpm run typecheck              # tsc across the workspace
pnpm run format-and-lint        # biome check
pnpm run format-and-lint:fix    # biome check --write
pnpm run check                  # biome check --write (used by lint-staged)

pnpm run build                  # build all workspaces
pnpm run dokploy:build          # build only the dokploy app
```

Inside `apps/dokploy`:

```bash
pnpm run test                   # vitest, tests under apps/dokploy/__test__/**/*.test.ts
pnpm exec vitest run __test__/permissions/check-permission.test.ts   # single test file
pnpm exec vitest -t "test name pattern"                              # filter by name

pnpm run migration:generate     # drizzle-kit generate (after editing schema in packages/server/src/db/schema)
pnpm run migration:run          # apply migrations
pnpm run db:studio              # drizzle studio
pnpm run db:seed / db:clean     # seed / truncate

pnpm run reset-password         # CLI to reset a user's password against the running DB
pnpm run generate:openapi       # regenerate root openapi.json from tRPC routers
```

Drizzle config lives at `apps/dokploy/server/db/drizzle.config.ts` but reads schema from `packages/server/src/db/schema`. SQL migrations are committed under `apps/dokploy/drizzle/`.

## Server package dev/prod modes

`packages/server` ships in two modes via its `package.json` exports, toggled by scripts:
- `pnpm --filter=server run switch:dev` (aliased as `server:script` from root) → `exports."."` points at `./src/index.ts`. Required for `dokploy:dev` to pick up live source.
- `pnpm --filter=server run switch:prod` → points at `./dist/...`. Build pipelines invoke this; you typically don't need to.

If imports from `@dokploy/server` resolve to stale compiled output during dev, re-run `pnpm run server:script`.

## Architecture

### Request flow (apps/dokploy)

Next.js Pages Router serves the UI. The custom server (`apps/dokploy/server/server.ts`) wraps `next()` with a plain `http.Server`, attaches WebSocket handlers, and on production startup also bootstraps Traefik config, cron jobs, schedules, and the BullMQ deployment worker. `IS_CLOUD` (env-driven, defined in `@dokploy/server/constants`) gates self-hosted-only initialization (Traefik setup, local Docker stats WS, in-process deployment worker) — in cloud mode those run elsewhere.

API surface:
- **tRPC** at `/api/trpc/*` via `apps/dokploy/pages/api/[...trpc].ts`. Root router: `apps/dokploy/server/api/root.ts`. Per-feature routers under `apps/dokploy/server/api/routers/*.ts`. Routers are thin — they validate input with Zod, enforce permissions, then delegate to service functions in `@dokploy/server/services/*`.
- **REST/OpenAPI** generated from tRPC via `@dokploy/trpc-openapi` meta on procedures; `openapi.json` at the repo root is the public spec, regenerated by `pnpm run generate:openapi`.
- **WebSockets** on the same HTTP server: docker logs, docker terminal, docker stats, deployment logs, drawer logs, server SSH terminal — see `apps/dokploy/server/wss/`.

### tRPC procedures (apps/dokploy/server/api/trpc.ts)

When adding a tRPC route, pick the right base procedure:
- `publicProcedure` — unauthenticated.
- `protectedProcedure` — requires session.
- `adminProcedure` / `cliProcedure` — owner or admin only.
- `enterpriseProcedure` — owner/admin AND a valid enterprise license for the active org.
- `withPermission(resource, action)` — fine-grained permission check via `checkPermission`. Use this for anything resource-scoped; resources/actions are declared in `packages/server/src/lib/access-control.ts`. Static roles (owner/admin/member) bypass enterprise-only resources; custom roles require an enterprise license. New resources/actions must be added to `statements` in `access-control.ts`.

Context exposes `ctx.session.activeOrganizationId` — most service calls scope by this.

### Shared package boundary (`@dokploy/server`)

`packages/server/src/index.ts` is a flat re-export. New service files added under `packages/server/src/services/` need an `export * from "./services/your-file"` line there to be importable by the apps. The dokploy app imports almost everything via `@dokploy/server` (services, DB, auth, builders, Traefik utils, constants, types).

Notable subtrees inside `@dokploy/server`:
- `services/` — domain logic (one file per resource: application, compose, postgres, deployment, project, …; proprietary/ holds enterprise-only services).
- `db/schema/` — Drizzle table definitions; `db/validations/` — Zod schemas derived via `drizzle-zod`.
- `utils/builders/` — build-strategy implementations: `dockerfile`, `nixpacks`, `paketo`, `railpack`, `heroku`, `static`, `compose`, `drop`.
- `utils/traefik/` — generates Traefik dynamic config files (applications, domains, middlewares, redirects, security, web-server).
- `utils/servers/remote-docker.ts` — SSH-tunneled Docker socket for multi-server deployments.
- `lib/auth.ts` — better-auth wiring (organizations, SSO, API keys, custom roles).
- `lib/access-control.ts` — RBAC statements + enterprise gating.
- `monitoring/`, `templates/processors/`, `setup/` — server bootstrap, traefik defaults, postgres/redis setup, monitoring stack.

### Deployments

`apps/dokploy/server/queues/deployments-queue.ts` defines a BullMQ `Worker` on the `deployments` queue. Self-hosted runs the worker in-process (started from `server.ts`); cloud delegates to `apps/api` via Inngest. Deployment jobs branch on `applicationType` (`application` / `compose` / `previewDeployment`) and `type` (`deploy` / `redeploy`), then call into `@dokploy/server` (`deployApplication`, `deployCompose`, `deployPreviewApplication`, `rebuild*`, `update*Status`).

### Frontend

- `apps/dokploy/pages/dashboard/**` — authed dashboard pages.
- `apps/dokploy/components/{ui,dashboard,layouts,shared,proprietary}` — UI is shadcn/ui + Radix + Tailwind. `proprietary/` and `pages/dashboard/**/proprietary` mirror the `services/proprietary` split for enterprise-gated UI.
- `lib/auth-client.ts` — better-auth client (organizations, SSO, custom roles).
- React 18.2, Next 16, TanStack Query, react-hook-form + zod resolvers.

## Conventions

- **Biome** is the only formatter/linter (`biome.json`). Don't introduce Prettier or ESLint configs. lint-staged runs `biome check --write` on commit.
- **Commit messages** follow Conventional Commits (`feat:`, `fix:`, `refactor:`, …). PRs go to `canary`.
- **Imports**: prefer `@dokploy/server/...` from app code, not deep relative paths into `packages/server/src/...`.
- **Permissions**: resource-scoped tRPC mutations should use `withPermission(...)` rather than ad-hoc role checks, so custom roles work.
- **Cloud vs self-hosted**: gate self-hosted-only behavior behind `if (!IS_CLOUD)`. Don't assume Docker is local — many flows tunnel via SSH using `remote-docker.ts`.
- **Schema changes**: edit `packages/server/src/db/schema/*.ts`, run `pnpm --filter=dokploy run migration:generate`, commit the generated SQL under `apps/dokploy/drizzle/`.

## Testing

Vitest, configured at `apps/dokploy/__test__/vitest.config.ts`. The setup file aliases `@dokploy/server` to `packages/server/src` so tests run against source. Test buckets: `permissions/`, `deploy/`, `compose/`, `cluster/`, `traefik/`, `templates/`, `wss/`, `requests/`, `server/`, `env/`, `drop/`, `utils/`. Tests use `pool: "forks"` — they can spawn child processes and shell out.
